### 术语约定

| 术语 | 含义 |
|---|---|
| **OID / OBJECTID** | 要素或行的唯一编号，本库中恒等于「槽位号 + 1」 |
| **槽位（slot）** | `.gdbtablx` 中的行指针数组下标，是 OID 的物理来源 |
| **要素类（Feature Class）** | 带几何字段的表，对应 `FeatureClass` |
| **表（Table）** | 不带几何的属性表，对应 `TableHandle` |
| **游标（Cursor）** | 遍历 / 更新 / 插入一行或要素的句柄，对应 ArcEngine 的 `ICursor` |
| **落盘（flush）** | 把内存中的表全量写回 `.gdbtable` + `.gdbtablx` 两个文件 |
| **保槽删除** | 删除行时保留 OID 编号空间，不让其他行的 OID 发生漂移 |

## 第 1 层 · 项目定位与能力边界

**这一层回答：这个项目是什么，能做什么，不能做什么？**

### 1.1 是什么

`gdb-rs` 是一个 **零外部依赖** 的纯 Rust 库，用于直接读写 ESRI File Geodatabase
（`.gdb` 文件夹）格式。它不依赖 ArcEngine、GDAL/OGR 或任何 C 库，目标是让地理数据
的读写能在 Rust 生态中独立、可控地完成。

工程形态：

```
gdb-rs（workspace）
├── crates/gdb_core   核心库：格式解析、对象模型、游标、查询、编辑、序列化
└── crates/gdb_cli    命令行工具：sample / list / describe / read / insert / update / delete
```

- Rust 2021 edition，**无任何第三方依赖**（`gdb_core` 的 `Cargo.toml` 无 `[dependencies]`；
  `gdb_cli` 仅依赖同 workspace 的 `gdb_core`）
- 源码 20 个文件约 6600 行（`gdb_core/src` 19 个 5699 行 + `gdb_cli/src/main.rs` 894 行），
  连同 3 个测试文件共约 7700 行
- 测试 59 个（32 单元 + 18 CRUD + 7 真实 gdb + 2 往返 + 1 文档测试）
- 可交叉编译为 Windows 可执行程序（`build-windows.sh` → `dist/gdb.exe`）

### 1.2 设计取向

代码组织**参考 ArcGIS ArcEngine 的对象模型**，而非照搬：

| ArcEngine 概念 | 本库落点 | 说明 |
|---|---|---|
| 工作空间 `IWorkspace` | `Geodatabase` | 打开 `.gdb`，枚举其中对象 |
| 要素类 `IFeatureClass` | `FeatureClass` | 带几何的表 |
| 表 `ITable` | `TableHandle` | 无几何的属性表 |
| 游标 `ICursor` | `Cursor` | `Search` / `Update` / `Insert` 三态 |
| 行 `IRow` / 要素 `IFeature` | `Row` / `Feature` | 字段访问与几何访问 |
| 查询过滤 `IQueryFilter` | `QueryFilter` | 属性条件 |
| 空间过滤 `ISpatialFilter` | `SpatialFilter` | 空间关系条件 |
| 编辑会话 `IWorkspaceEdit` | `EditSession` | 事务与回滚 |

> **重要说明**：本库**没有**定义 `ITable` / `IFeatureClass` 这类 trait。全库零 trait，
> 全部以具体类型表达。这是有意的选择：ArcEngine 的多态建立在 COM 之上，而本库用
> `Rc<RefCell<Table>>` 共享所有权已经足够，引入 trait 会增加复杂度却收益有限。
> 命名与语义对齐，但**不追求接口形态的机械一致**。

### 1.3 明确的能力边界

**支持**

- 解析 `.gdb` 目录中的独立要素类、独立数据表、要素数据集内的要素类
- 读取全部字段类型与几何（Point / MultiPoint / Polyline / Polygon）
- 按 OID、OID 集合、属性条件（where 子句）、空间关系过滤
- 增（插入新行 / 新要素）、删（按条件 / 按 OID 批量删）、改（改属性 / 改几何）
- 编辑会话：嵌套操作、快照回滚、提交落盘
- 序列化回写 `.gdbtable` / `.gdbtablx`

**不支持（当前版本）**

- ❌ **无 SQL 引擎**：不支持 `SELECT ... FROM ...`，仅支持 where 子句形式的过滤
- ❌ **不写索引**：`.atx`（属性索引）、`.spx`（空间索引）、`.gdbindexes` 全部不读取也不写回
- ❌ **不写 `.freelist`**：删除产生的空槽不会被回收复用
- ❌ **无几何构造算子**：没有 buffer / clip / union / 平移 / 旋转等，空间能力只有布尔判定
- ❌ **单线程**：`Rc<RefCell<>>` 模型，非 `Send` / `Sync`
- ❌ **不改 Schema**：字段定义只增不改，编辑会话的快照也不覆盖 schema

## 第 2 层 · 五分钟上手

**这一层回答：怎么用？给我能跑的代码。**

### 2.1 打开数据库并查看内容

```rust
use gdb_core::Geodatabase;

let gdb = Geodatabase::open(std::path::Path::new("test.gdb"))?;

// 列出所有要素类与表
for item in gdb.items() {
    println!("{:?} {}", item.item_type, item.name);
}

let fc = gdb.open_feature_class("地块")?;
println!("要素数: {}", fc.feature_count());
```

等价 CLI：

```bash
gdb list test.gdb
gdb describe test.gdb 地块
```

### 2.2 查询（Search 游标）

```rust
use gdb_core::{QueryFilter, SpatialRel};

// 属性条件
let mut cur = fc.search(&QueryFilter::where_clause("编号 >= 1 AND SZ > 100")?)?;
while let Some(f) = cur.next_feature() {
    println!("OID={} BH={:?}", f.object_id(), f.get_by_name("BH")?);
}

// 空间条件：与给定多边形相交
let mut cur = fc.search(&QueryFilter::intersected(polygon)?)?;
```

> 迭代中若要删除，**不要**在同一个 Update 游标里边遍历边删。正确范式是
> 「先 Search 收集，再 Update 删」（原因见第 6.1 节）。

### 2.3 更新（Update 游标）

```rust
let mut cur = fc.update(&QueryFilter::where_clause("BH = '编号1'")?)?;
while let Some(f) = cur.next_feature() {
    f.set_by_name("SZ", FieldValue::Double(999.0))?;
    cur.update(f.row())?;   // 写回
}
fc.save()?;                 // 落盘
```

### 2.4 用编辑会话保证可回滚

```rust
let session = gdb.edit_session();
session.start();
session.start_operation()?;

let fc = session.open_feature_class(&gdb, "地块")?;   // 经会话打开才会登记
// ... 各种增删改 ...

session.stop_operation()?;
session.commit()?;      // 提交落盘
// 或 session.abort();  // 回滚到操作开始前
```

等价于 CLI 的 `--dry-run` 与事务语义。

**关键提醒**：只有经 `session.open_feature_class()` / `session.open_table()` 打开的对象
才会被登记进编辑会话、才有快照可回滚。自行 `gdb.open_feature_class()` 打开的对象
**不受事务保护**（这是现存缺口，见第 8 层第 4 项）。

→ 理解了用法，下面进入概念模型，看这些对象之间如何组织。

## 第 3 层 · 核心概念模型

**这一层回答：有哪些对象，它们之间什么关系，生命周期如何？**

### 3.1 对象全景

```
                        ┌─────────────────┐
                        │  Geodatabase    │  工作空间：打开 .gdb，枚举/打开其中对象
                        │  (IWorkspace)   │
                        └────────┬────────┘
                                 │ open_feature_class / open_table
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
        ┌────────────────┐              ┌────────────────┐
        │  FeatureClass  │              │  TableHandle   │
        │ (IFeatureClass)│              │   (ITable)     │
        └───────┬────────┘              └───────┬────────┘
                │  search / update / insert     │
                └───────────────┬───────────────┘
                                ▼
                        ┌────────────────┐
                        │     Cursor     │  三态：Search / Update / Insert
                        │   (ICursor)    │
                        └───────┬────────┘
                                │ next_row / next_feature
                                ▼
                    ┌───────────────────────┐
                    │  Row        Feature   │  Feature = Row + 几何访问器
                    │ (IRow)     (IFeature) │
                    └───────────┬───────────┘
                                │ 共享底层
                                ▼
                    ┌───────────────────────┐
                    │  Table (Rc<RefCell>)  │  真正的存储：rows + row_slots
                    └───────────────────────┘

   辅助角色：
   QueryFilter  ──► 决定 Cursor 遍历哪些行
   EditSession ──► 包裹 Table，提供快照与回滚
```

### 3.2 所有权模型：一切共享同一个 `Table`

这是整个库最核心的结构决策：

```rust
pub struct FeatureClass {
    pub(crate) table: Rc<RefCell<Table>>,   // 共享引用，不是独占
    pub        item:  CatalogItem,
}
```

`FeatureClass`、`TableHandle`、`Cursor`、`Row`、`Feature` **全部持有同一个**
`Rc<RefCell<Table>>`。由此产生三个直接后果：

1. **多个游标可以同时存在**，它们看到的是同一份数据。
2. **`Row::set()` 取 `&self` 而非 `&mut self`** —— 因为修改的是共享的 `RefCell`，
   不需要 `Row` 自身可变。
3. **`Row::store()` 是空实现** —— 内存中修改已即时生效，`store` 仅为兼容 ArcEngine
   语义而保留。真正的持久化只发生在 `Table::flush()`。

> ⚠️ **编码铁律**：由于 `RefCell` 在运行时检查借用，任何「先借用读、再借用写」的
> 代码都必须遵循 **先取值副本 → 再 `borrow_mut()`** 的顺序，否则运行时 panic。
> 全库所有写路径（如 `Cursor::update`）都严格遵守这一范式。

### 3.3 游标三态

| 模式 | ArcEngine 对应 | 可做什么 | 产出 |
|---|---|---|---|
| `Search` | `IFeatureClass.Search` | 只读遍历 | `next_row()` / `next_feature()` |
| `Update` | `IFeatureClass.Update` | 遍历 + 更新 + 删除 | 同上 + `update()` / `delete_row()` |
| `Insert` | `IFeatureClass.Insert` | 插入新行 | `insert()` |

模式在运行期做门禁校验（例如 `Cursor::update` 在非 Update 模式返回
`Err(GdbError::Edit("update 仅允许在 Update 游标上调用"))`）。

### 3.4 生命周期

```
Geodatabase::open
   └─► 解析 GDB_SystemCatalog / GDB_Items / GDB_ItemTypes → items: Vec<CatalogItem>

gdb.open_feature_class("地块")
   └─► catalog 查到 file_id → Table::open(dir, file_id)
        ├─ 读 .gdbtable：解析 schema（字段描述段）
        ├─ 读 .gdbtablx：读出所有槽位号
        └─ 逐槽 decode_row → rows / row_slots
   └─► FeatureClass { table: Rc::new(RefCell::new(t)), item }

fc.search(&filter)
   └─► Cursor::new(table.clone(), Search, filter)
        └─► matching_indices()：一次性算出所有匹配行的下标

cur.next_feature()
   └─► Row::new(table.clone(), index) → Feature::new(row)
```

## 第 4 层 · 数据模型与文件格式

**这一层回答：`.gdb` 里到底是什么？为什么 OID 等于槽位 + 1？**

### 4.1 目录结构

一个 `.gdb` 是一个**文件夹**，其中每张表由一组 `aNNNNNNNN.*` 文件构成：

```
test.gdb/
├── gdb                     元信息
├── timestamps              时间戳
├── a00000001.gdbtable      系统表（TablesByName）
├── a00000001.gdbtablx
├── a00000001.gdbindexes    索引目录（描述本表有哪些索引）
├── a00000001.TablesByName.atx   属性索引
├── a00000004.gdbtable      系统表（GDB_Items / CatItems）
├── a00000004.spx           空间索引
├── a00000004.freelist      空闲槽位链表
├── a00000009.gdbtable      用户要素类
├── a0000000a.gdbtable      用户要素类「地块」（2.4 MB，6151 个要素）
└── ...
```

本库当前**只读写 `.gdbtable` 与 `.gdbtablx` 两种**，其余（`.atx` / `.spx` /
`.gdbindexes` / `.freelist`）一律忽略。

### 4.2 两个文件的分工

| 文件 | 职责 | 内容 |
|---|---|---|
| `.gdbtable` | **存数据** | 40 字节头 + 字段描述段 + 逐行的值 blob |
| `.gdbtablx` | **存指针** | 槽位数组：第 N 个槽记录第 N 行在 `.gdbtable` 中的字节偏移 |

`.gdbtable` 头部布局（小端）：

| 偏移 | 字段 |
|---|---|
| 0 | version（3 或 4） |
| 4 | 行数（v3）；v4 在偏移 16 |
| 8 | largest（最大行字节数） |
| 24 | 文件总大小 |
| 32 | 字段描述段偏移（恒为 40） |

每行 blob 的结构：

```
[i32 row_len][null 位图][按字段顺序排列的值流]
```

`.gdbtablx` 结构：

```
[i32 version=3][i32 n1024blocks][i32 nrows][i32 offset_size]
然后是 nrows 个槽位偏移，每个占 offset_size 字节（4 / 5 / 6 由最大偏移决定）
```

### 4.3 OID = 槽位 + 1（本库最重要的不变量）

**ObjectId 字段并不存储在行内。** 它是打开时由槽位号合成的：

```rust
// decode_row 内部
values.push(FieldValue::ObjectId(slot + 1));
```

也就是说：`.gdbtablx` 里第 N 个槽位（从 0 计）对应的行，其 OID 就是 `N + 1`。

这个不变量直接决定了三个行为：

> **保槽删除**：删除一行时，`rows` 与 `row_slots` **同步移除该元素**，但 `slot_count`
> **不变**。序列化时该槽位写入 `offset = 0`（表示空槽）。于是**删除后其他行的 OID
> 完全不变** —— 这正是 ArcGIS 的行为。
>
> **新行不复用空槽**：`add_row` 永远追加到 `slot_count` 位置，故新 OID =
> `slot_count + 1`。即使前面有被删除留下的空槽也不会复用（实测：地块表删空后
> 再插入，OID 从 6 开始而非 2）。
>
> **不写 `.freelist`**：空槽不会被登记为空闲，因此不参与回收。

维护 `rows` 与 `row_slots` 的同步是全库的硬性约束（`Table::delete_row` 内有
`debug_assert_eq!`）。

### 4.4 字段描述与类型

字段定义（`FieldDef`）包含：

```rust
pub struct FieldDef {
    pub name: String,
    pub alias: String,
    pub field_type: FieldType,
    pub nullable: bool,      // flags bit0 (0x01)
    pub required: bool,      // flags bit1 (0x02)
    pub editable: bool,      // flags bit2 (0x04)
    pub length: i32,         // 仅 String 有意义
    pub grid: PrecisionGrid, // 仅 Geometry 有意义
    pub srs_wkt: String,     // 仅 Geometry 有意义
    pub geom_has_z: bool,    // gflag bit2
    pub geom_has_m: bool,    // gflag bit1
    pub default: Option<FieldValue>,
}
```

`FieldType` 共 16 个编码值（`Int16=0` … `Int64=13`，`Uuid` 占 10/11，其它归 `Other(u8)`）。
`GeometryType` 编码：`None=0, Point=1, MultiPoint=2, Polyline=3, Polygon=4,
Envelope=5, MultiPatch=9`。

### 4.5 几何的整数量化（PrecisionGrid）

几何坐标在文件中**以整数存储**，通过精度网格换算：

```rust
pub struct PrecisionGrid {
    pub xorig: f64, pub yorig: f64, pub xyscale: f64,
    pub zorig: f64, pub zscale: f64,
    pub morig: f64, pub mscale: f64,
    pub xytol: f64, pub mtol: f64, pub ztol: f64,
    pub extent: (f64, f64, f64, f64),
    pub grid_sizes: Vec<f64>,   // 空间索引网格参数（当前无消费者）
}
```

换算公式：

```
grid = ((x - xorig) * xyscale).round()     // 真实坐标 → 网格整数
x    = grid / xyscale + xorig              // 网格整数 → 真实坐标
```

默认值 `xyscale = 1e9`、`xorig = -2147483647`，即约 1 纳米级精度。

> ⚠️ **已知问题**：`serialize_table` 在写回时把 `fdef.grid.extent` **原样回写**，
> 不会因几何更新而重算。若写入超出原范围的几何，文件头的范围信息会失真。
> 同样地，Z/M 范围目前恒定写 0。

→ 文件格式清楚了，下一层看代码模块如何分层。

## 第 6 层 · 核心机制深入

**这一层回答：最关键的六个机制具体是怎么工作的？**

### 6.1 游标与 `remap` 索引重定位

`Cursor` 的结构：

```rust
pub struct Cursor {
    table:   Rc<RefCell<Table>>,
    mode:    CursorMode,
    indices: Vec<usize>,   // 构造时一次性算出的匹配行下标
    pos:     usize,        // 已消费计数，下一次返回 indices[pos]
}
```

**关键设计**：匹配集合在**构造时一次性算完**（快照式），之后遍历只是沿 `indices`
前进。好处是遍历期间不必重复求值；代价是**表在遍历中发生变化时，`indices` 会失效**。

为此引入纯函数 `remap`：

```rust
pub(crate) fn remap(indices: Vec<usize>, pos: usize, removed: usize) -> (Vec<usize>, usize)
```

契约与三类情形：

| 情形 | 处理 | `pos` 变化 |
|---|---|---|
| 删除**已消费**项（在 `indices[..pos]` 中） | 移除该项，后续左移 | `pos - 1` |
| 删除**未消费**项（在 `indices[pos..]` 中） | 移除该项，后续左移 | 不变 |
| 删除**不匹配**项（不在 `indices` 中） | 集合仅左移 | 不变 |

实现要点：丢弃 `== removed` 的项；`> removed` 的项全部 `-1`；再按被删项是否落在
已消费区间决定 `pos` 是否减 1。该函数有 **8 个单元测试**专门覆盖。

> ⚠️ **为什么不能边遍历边删**：删除会使 `rows` 整体左移，`indices` 中尚未消费的下标
> 全部失效。虽然 `remap` 能修正，但**删除当前正在处理的行**语义极易出错。因此库内
> 推荐范式是「先 Search 收集 → 再 Update 删除」，与 ArcEngine 一致。

### 6.2 查询过滤：六形态与 where 子句解析

```rust
pub enum QueryFilter {
    All,                                    // 全部行
    ByOid(u64),                             // 单个 OID
    ByOids(Vec<u64>),                       // OID 集合
    Where(WhereClause),                     // 属性条件
    Spatial(SpatialFilter),                 // 空间条件
    Combined { where_clause: WhereClause, spatial: Option<SpatialFilter> },  // 组合
}
```

`is_oid_only()` 判定 `All` / `ByOid` / `ByOids`，走**零克隆快路径**；复杂条件
（属性 / 空间）走慢路径。

**where 子句解析器**是手写的递归下降实现（纯 std，无正则、无第三方库）：

```
词法 lex：Ident（含 "带引号字段名"） / Str（'...'，'' 转义，CJK 安全）
         / Num / Int / 关键字 AND OR NOT IS NULL IN TRUE FALSE
         / 操作符 = == <> != > >= < <= / ( ) ,

语法（优先级由低到高）：
  or_expr   := and_expr (OR and_expr)*
  and_expr  := primary (AND primary)*
  primary   := '(' or_expr ')' | NOT primary | predicate
  predicate := field op literal
             | field IS [NOT] NULL
             | field [NOT] IN (literal, ...)

AST：Expr::{ True, And, Or, Not, Cmp{field,op,value},
             IsNull{field,negated}, In{field,values,negated} }
```

求值由 `eval(&Expr, &[FieldValue], &TableSchema) -> bool` 完成，辅以
`lookup` / `as_num` / `as_text` / `cmp_num` / `cmp_text` / `cmp_bool` / `apply_op`。
`lookup` 先精确匹配字段名，失败后做 ASCII 大小写不敏感兜底。

**慢路径的性能代价**：

```rust
let (rows, schema, oi, gi) = {
    let t = table.borrow();
    (t.rows.clone(), t.schema.clone(), ...)   // 整表克隆！
};
```

为避免求值期间重入 `RefCell` 借用，慢路径会**整表 clone**。对 6151 行 × 40 字段的
表，这是一次可观的 O(N) 拷贝。此外，快路径 OID 回退值为 `0`、慢路径为 `i + 1`，
两路径不一致，是潜在的不一致点。

### 6.3 精确空间谓词

`geometry/predicate.rs` 提供真正的几何判定（而非粗糙的包络框比较），`EPS = 1e-9`：

| 函数 | 作用 |
|---|---|
| `point_on_segment` | 点是否在线段上 |
| `segments_intersect` | 两线段是否相交（含共线、端点接触） |
| `point_in_ring` | 射线法判定点在环内 |
| `point_in_polygon` | **先判边界，再奇偶规则** —— 正确处理带洞多边形 |
| `intersects` / `contains` / `within` | 三种空间关系 |

`SpatialFilter::matches` 的策略是**先包络框粗筛，再精确判定**：

```rust
pub enum SpatialRel { EnvelopeIntersects, Intersects, Contains, Within }
```

正确性由一个专门的测试保证：构造一个「甜甜圈」查询几何（外环覆盖 OID=2 的包围盒，
内环正好挖掉 OID=2），断言命中数为 0 —— 证明是精确判定而非包围盒判定。

### 6.4 编辑会话与快照回滚

```rust
pub struct EditSession {
    tables:    RefCell<Vec<Rc<RefCell<Table>>>>,
    started:   Cell<bool>,
    op_depth:  Cell<usize>,
    op_stack:  RefCell<Vec<String>>,
    snapshots: RefCell<Vec<(Rc<RefCell<Table>>, TableSnapshot)>>,
}
```

`TableSnapshot` 只快照可变的行状态：

```rust
pub(crate) struct TableSnapshot {
    pub rows: Vec<Vec<FieldValue>>,
    pub row_slots: Vec<u64>,
    pub slot_count: u64,
}
```

（**不含 schema**，故字段定义的改动无法回滚。）

工作流：

```
start()                     → started = true
start_operation()           → 若 op_depth == 0（最外层），对全部已登记表重建快照
                            → op_depth += 1
  ... 增删改 ...
stop_operation()            → op_depth -= 1
commit()                    → 要求 started && op_depth == 0；逐个 flush() 落盘
abort()                     → 逐个 restore(snapshot) 回滚内存
```

嵌套 `start_operation` 时只有**最外层**建立快照，因此内层操作的失败会连带回滚到
最外层开始处 —— 这与 ArcEngine 的编辑操作语义一致。

> ⚠️ **两个边界行为**（已被测试固化）：
> - 未调用 `start_operation()` 就 `abort()` → snapshots 为空 → **内存改动保留，
>   仅不写盘**。
> - `register()` 是私有的，只能通过 `session.open_*` 登记。用户自行 `gdb.open_*`
>   打开的对象**完全没有快照保护**。

### 6.5 序列化与落盘

**落盘只有一条路径**：

```
Table::flush(&self)
  └─ serialize() → serialize_table(&Table) → (table_bytes, tablx_bytes)
       ├─ 1. 字段描述段（fdesc_version = 6 if version==4 else 4）
       ├─ 2. 逐行 encode_row → [i32 len][null 位图][值流]
       ├─ 3. 拼 .gdbtable：40 字节头 + fdesc + 行 blob
       └─ 4. 拼 .gdbtablx：槽位偏移数组，空槽写 0
  └─ fs::write(a{id:08x}.gdbtable) + fs::write(a{id:08x}.gdbtablx)
```

要点：

- **没有行级写入、没有 WAL、没有增量**：每次 `flush` 都是**整表全量重写**，
  O(文件大小)。
- 因此**批量修改后只应调用一次 `flush`**；若在循环内 flush，会退化成
  O(N × 文件大小)。
- `flush(&self)` 取共享引用，可在只有 `&self` 的地方调用。
- 槽位数组的兜底分支需警惕：若 `row_slots.len() != rows.len()`，会退化为
  `(0..rows.len())` 重排槽位，导致 **OID 漂移**。任何改动 `rows` / `row_slots`
  的新代码都必须保持二者同步。

### 6.6 保槽删除（回顾）

三条操作对槽位的影响：

| 操作 | `rows` | `row_slots` | `slot_count` | 落盘后 |
|---|---|---|---|---|
| 删除 | 移除该元素 | **同步移除** | 不变 | 该槽 `offset=0`（空槽），其余 OID 不变 |
| 插入 | push | push(`slot_count`) | `+1` | 新 OID = 原 `slot_count + 1` |
| 清空 | clear | clear | **未清** | 下次 `slot_count` 会退化为 0，OID 从 1 重来 |

第三条是一个已识别的缺口（见第 8 层第 6 项）。

## 第 9 层 · 规划目标态设计

### 9.1 SQL 查询引擎

**目标**：支持 `SELECT` / `UPDATE` / `DELETE` 三种语句，用于「查询数据表信息」与
「非空间属性更新」。

**新增模块**：`crates/gdb_core/src/sql.rs`

```rust
pub enum Statement {
    Select { fields: Vec<SelectItem>, from: String,
             where_: Option<WhereClause>, order_by: Vec<OrderBy>, limit: Option<usize> },
    Update { table: String, set: Vec<(String, Literal)>, where_: Option<WhereClause> },
    Delete { table: String, where_: Option<WhereClause> },
}
pub fn parse(sql: &str) -> Result<Statement>
```

**复用策略（重要）**：现有 `query_filter.rs` 的整块资产可直接复用 ——

| 可复用 | 说明 |
|---|---|
| `lex` / `Tok` | 字符串转义、`''`、双引号字段名、Unicode 标识符、数字扫描 |
| `parse_literal` | 字面量解析 |
| `parse_or` / `parse_and` / `parse_primary` | 优先级骨架，直接作为表达式层 |
| `eval` / `lookup` / `as_num` / `as_text` / `cmp_*` / `apply_op` | **整块作为 WHERE 求值器** |
| `SpatialFilter` / `SpatialRel` / `predicate` | 空间谓词 |

**必须改造**：

- `lex` 当前对 `*`、`;`、`.`、`%` 直接报「未知字符」 —— 需新增 `Star` / `Semi` /
  `Dot` 等 token，并扩充关键字表（`SELECT` / `FROM` / `WHERE` / `ORDER` / `BY` /
  `LIMIT` / `UPDATE` / `SET` / `DELETE` / `LIKE` / `BETWEEN` / …）。现有关键字表
  只有 `AND OR NOT IS NULL IN TRUE FALSE` 八个。
- `Expr` 需从「`field OP literal`」升级为**表达式树**（支持列 vs 列、算术、
  函数、别名）。
- `Tok` / `Expr` / `CmpOp` / `Literal` / `Parser` **当前全部私有**，需放宽可见性
  或将 SQL 解析器并入 `query_filter.rs`。
- 新增入口 `Geodatabase::execute_sql(&str) -> Result<QueryResult>`；表名解析需
  放宽现有私有的 `find`（当前是严格 `==`，应改为大小写不敏感）。
- `FieldValue` 需补格式化能力（把 CLI 的 `show_value` / `geom_to_wkt` 下沉到 core）。

**范围建议**：优先实现**核心子集**（`SELECT` 列/星号 + `WHERE` + `ORDER BY` +
`LIMIT`；`UPDATE ... SET ... WHERE`；`DELETE FROM ... WHERE`）。聚合（`COUNT` /
`SUM` / `GROUP BY`）与 `JOIN` 建议后置 —— FileGDB 本身无 SQL 引擎，多表 JOIN
需自行实现嵌套循环，工程量大而收益有限。

**性能提醒**：SQL 批量更新后**只调用一次 `flush`**；`matching_indices` 的全表
clone 是主要瓶颈，可改为「不 clone，逐行 `borrow()` 求值」。

### 9.2 空间数据更新

**目标**：补齐「写几何 → 自动维护 `Shape_Length` / `Shape_Area`」这一核心闭环。

**首要改动**：

1. 在 `src/geometry/mod.rs` 新增公开函数（把测试里的私有实现上提到 `src/`）：
   ```rust
   pub fn length(g: &Geometry) -> f64
   pub fn area(g: &Geometry) -> f64
   ```
   面积需处理带洞多边形，且判定规则要与 `predicate::point_in_ring` 的奇偶规则一致。

2. `TableSchema` 新增辅助方法（大小写不敏感匹配）：
   ```rust
   pub fn shape_length_index(&self) -> Option<usize>
   pub fn shape_area_index(&self) -> Option<usize>
   ```

3. `Feature::set_geometry` 写入几何后，按 schema 是否含这两个字段**自动重算并回填**，
   复现 ArcGIS 行为。需处理：字段名大小写变体、字段可空性、点/多点几何时置 0 或 NULL。

4. 新增 `Feature::{shape, set_shape}` 别名（对齐 `IFeature.Shape`）与
   `FeatureClass::shape_field_name()`（对齐 `IFeatureClass.ShapeFieldName`）。

5. `serialize_table` 的 `fdef.grid.extent` 按全表几何重算。

**可选扩展**：几何编辑算子（平移 / 缩放 / 旋转 / buffer / clip / simplify）。
这需要**全新**的构造型几何模块 —— 现有 `predicate.rs` 只有布尔判定，没有任何
几何构造能力。建议作为独立阶段。

### 9.3 游标 buffer 模型改造

**目标**：让 Insert 游标符合 ArcEngine `Insert → buffer → Store` 模型，并修复现存 bug。

**必须修复**：

- `FeatureClass::insert()` 在 `Insert` 模式下应令 `indices` 为**空**（当前被
  `QueryFilter::All` 填成全表，导致 `next_row()` 错误产出已有行）。
- `Cursor::insert` 返回值改为 `Result<u64>`，返回新 OID。

**新增**：

```rust
impl Cursor {
    pub fn create_row(&mut self) -> Result<Row>        // ArcEngine InsertCursor buffer
    pub fn create_feature(&mut self) -> Result<Feature>
    pub fn insert_row(&mut self, values: Vec<FieldValue>) -> Result<u64>
}
```

**取舍建议**：保留 `create_feature` / `create_row` 作为**便捷包装**（内部走
Insert 游标），而不是删除它们 —— 这样既符合 ArcEngine 游标模型，又不破坏现有
18 个 CRUD 测试与 CLI。

**架构取向**（三种并列，供决策）：

| 方案 | 收益 | 代价 |
|---|---|---|
| **A. 保持具体类型，对齐语义**（推荐） | 不破坏现有 59 个测试与 CLI，风险最低 | ArcEngine 接口形态贴合度一般 |
| B. 引入 trait 抽象层（`ITable` / `IFeatureClass` / `ICursor`），具体类型实现 | 贴合度最高 | 触及 `lib.rs` 导出面与全部调用点 |
| C. 完全 trait object（`Box<dyn ICursor>`） | 最贴近 COM 风格 | 与现有 `Rc<RefCell>` 共享所有权模型冲突，改动最大 |

### 9.4 关于索引（`.atx` / `.spx`）

当前零利用。若要启用：`.gdbindexes`（UTF-16LE 索引目录，描述每张表有哪些索引）
是解析入口；`.atx` 与 `.spx` 的结构均为「22 字节头 + N × 1024 字节页」。
这需要从零逆向实现，**建议列为最远期** —— 短期全表扫描对当前数据规模（6151 行）
完全够用。

## 附录 · 速查

**核心不变量**

```
OID = 槽位号 + 1              ObjectId 不存于行内，由槽位合成
删除 = rows/row_slots 同步移除，slot_count 不动 → 其余 OID 不变
插入 = 追加到 slot_count，新 OID = slot_count + 1，不复用空槽
落盘 = Table::flush() 整表全量重写（唯一入口，无行级写、无 WAL）
内存 = Row::set / set_geometry 直接改 RefCell；store() 为空实现
铁律 = 先取值副本 → 再 borrow_mut()，避免 RefCell 重入 panic
```

**关键文件**

| 文件 | 为什么重要 |
|---|---|
| `crates/gdb_core/src/table.rs` | 表模型 + 编解码 + 落盘，最复杂（1055 行） |

| `crates/gdb_core/src/feature_class.rs` | 对外对象层 API |
